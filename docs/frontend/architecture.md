# Архитектура Frontend (Feature-Sliced Design)

**Проект:** Мобильный маркетплейс «Т-Маркет» (Т-Образование / JDEPH-93)  
**Роль в команде:** Frontend Developer  
**Методология:** Feature-Sliced Design (FSD v2)  
**Тип приложения:** Client-Side Single Page Application (SPA)

---

## 1. Стек технологий

Стек сформирован с соблюдением требований ТЗ, индустриальных стандартов Т-Банка и принципов высокой производительности на мобильных устройствах:

| Категория | Технология | Назначение |
| :--- | :--- | :--- |
| **Язык** | **TypeScript 5** | Статическая типизация DTO, интерфейсов и исключение ошибок на этапе компиляции |
| **Базовая библиотека** | **React 18** | Компонентная декларативная модель, хуки состояния и эффектов |
| **Сборщик** | **Vite** | Быстрый HMR в разработке, Rollup для продакшн-бандлинга |
| **UI-система** | **Mantine v7** | Компонентная библиотека (`@mantine/core`, `@mantine/hooks`), нативные CSS Modules по канонам [ui.mantine.dev](https://ui.mantine.dev/) |
| **Стейт данных** | **TanStack Query v5** | Управление серверным состоянием (React Query), дедупликация, кэширование, авто-инвалидация |
| **Маршрутизация** | **React Router v7** | Клиентская навигация без перезагрузки страницы, защита роутов |
| **HTTP-клиент** | **Axios** | Централизованный клиент с очередями запросов, интерцепторами токенов и автоматическим Silent Refresh |
| **Архитектура** | **Feature-Sliced Design** | Чёткое разделение ответственности, модульность и однонаправленный поток зависимостей |

## 2. Модель безопасности и жизненный цикл сессии (JWT)

В соответствии с согласованной архитектурой хранение токенов оптимизировано для мгновенного отклика интерфейса и стабильности SPA:

### 2.1. Хранение токенов
* **`accessToken` (короткоживущий, ~15 минут):**
  * Сохраняется в **`localStorage`**, что гарантирует синхронное восстановление сессии при перезагрузке страницы (`F5`) без блокировок интерфейса и задержек.
  * Передаётся в заголовке `Authorization: Bearer <accessToken>` перед каждым запросом через Request Interceptor.
* **`refreshToken` (долгоживущий, ~7-30 дней):**
  * Устанавливается бэкендом в **`HttpOnly; Secure; SameSite=Strict` Cookie** с директивой `Path=/api/v1/auth`.
  * Браузер скрывает куку от клиентского JavaScript (`document.cookie` её не видит, защита от XSS).
  * Браузер автоматически отправляет её только на ручки аутентификации (`/api/v1/auth/refresh`, `/api/v1/auth/logout`).

### 2.2. Сценарии Silent Refresh (тихого обновления)
1. **Перезагрузка страницы (`F5`) или открытие новой вкладки:**
   * При монтировании фронтенд мгновенно считывает токен из `localStorage`.
   * Если токен отсутствует, выполняется фоновый тихий запрос `POST /api/v1/auth/refresh` по куке.
2. **Истечение срока токена на лету (`401 Unauthorized`):**
   * Перехватчик ответов Axios (`Response Interceptor`) перехватывает 401 статус.
   * Исходящие параллельные запросы ставятся в очередь ожидания (`failedQueue`).
   * Вызывается `POST /api/v1/auth/refresh`. При получении нового токена память и `localStorage` обновляются, и все запросы из очереди автоматически повторяются.
   * Если refresh-токен отозван или истёк — сессия сбрасывается, происходит мягкий редирект на экран входа.

## 3. Разделение сущностей пользователей и организаций (B2B / B2C)

Для поддержки командной работы продавцов и разграничения прав доступа сущность физического лица (`User`) отделена от юридического лица/магазина (`Organization`):

```text
               ┌───────────────────────┐
               │         User          │ (id, email, fullName, phone)
               └───────────┬───────────┘
                           │ 1:1
            ┌──────────────┴──────────────┐
            ▼                             ▼
┌───────────────────────┐   ┌───────────────────────────┐
│     BuyerProfile      │   │    OrganizationMember     │
│ (buyer_id, bonus,     │   │ (membership_id, role,     │
│  cart, deliveryAddrs) │   │  permissions / CASL)      │
└───────────────────────┘   └─────────────┬─────────────┘
     (Обязательный)                       │ N:1
                                          ▼
                            ┌───────────────────────────┐
                            │       Organization        │
                            │ (org_id, companyName,     │
                            │  inn, shopRating, goods)  │
                            └───────────────────────────┘
                                   (Опционально)
```

* **`User` (Физлицо):** Учётная запись человека (покупателя). В ней **нет жёстко зашитого `sellerId`**.
* **`BuyerProfile` (1:1):** Профиль покупателя (баланс бонусов, корзина, избранное, история покупок). Создаётся автоматически при регистрации.
* **`Organization` (Магазин / Юрлицо):** Профиль продавца (ИНН, название компании, банковские реквизиты, витрина товаров).
* **`OrganizationMember` (Членство и роли):** Связка между сотрудником и магазином. Позволяет нескольким людям (директор, менеджер, кладовщик) работать в одном кабинете продавца под своими личными учётками с разграничением прав (RBAC / CASL).

## 4. Стандарт обработки ошибок API (RFC 7807 / RFC 9457)

* **Ошибки полей форм (422 Unprocessable Entity):**
  * Бэкенд возвращает объект `details: Record<string, string>`.
  * Фронтенд напрямую передаёт его в `form.setErrors(details)`. Ошибки подсвечиваются прямо под нужными инпутами, без тостов.
* **Общие бизнес-ошибки (400, 401, 403, 404, 409, 500):**
  * Бэкенд возвращает `title` и `detail`.
  * Фронтенд автоматически выводит пользователю всплывающее уведомление (Toast / Notification).

## 5. Концепция Mobile-First и адаптивная верстка

Приложение спроектировано по принципу **Mobile-First** с бесшовной поддержкой десктопных экранов:

1. **Мобильный режим (`< 768px`):**
   * Навигация вынесена в нижний таббар (**`BottomNav`**) прямо под большой палец: `Главная`, `Каталог`, `Профиль / Вход`.
   * Верхняя шапка компактная (`52px`) — содержит только лаконичный логотип без дублирующих кнопок.
   * Контент имеет отступ снизу `padding-bottom: 76px`, чтобы нижний таббар не перекрывал элементы страницы.
   * Футер отображается над таббаром при прокрутке до конца.
2. **Десктопный режим (`>= 768px`):**
   * Нижний таббар скрывается (`display: none !important`).
   * Навигационные ссылки переезжают в верхнюю шапку.
   * Каталог автоматически масштабируется на адаптивную сетку Mantine `SimpleGrid`.

## 6. Иерархия слоев Feature-Sliced Design (FSD v2)

```text
src/
├── app/                  # Инициализация приложения, провайдеры, роутер
│   ├── providers/        # AppProviders (QueryClientProvider + MantineProvider + Router + Auth)
│   ├── router/           # AppRouter (декларативные маршруты)
│   └── App.tsx           # Корневой лейаут (Header + Content + Footer + BottomNav)
│
├── pages/                # Страницы маркетплейса
│   ├── home/             # Главная страница и витрина статуса
│   ├── catalog/          # Каталог с фильтрами по спецификации
│   ├── login/            # Вход и Личный кабинет покупателя
│   └── not-found/        # 404
│
├── widgets/              # Композиционные блоки интерфейса
│   ├── header/           # Верхняя шапка (HeaderSimple + CSS Module)
│   ├── navbar/           # Нижний мобильный таббар (BottomNav)
│   └── footer/           # Подвал приложения (FooterSimple + CSS Module)
│
├── entities/             # Бизнес-сущности
│   └── user/             # Модель пользователя
│       ├── api/          # authApi.ts (чистые функции запросов без React)
│       ├── model/        # AuthContext.tsx, types.ts
│       └── index.ts      # Публичный интерфейс
│
└── shared/               # Переиспользуемый базис без бизнес-логики
    ├── api/              # client.ts (Axios), queryClient.ts (TanStack Query)
    ├── theme.ts          # Конфигурация темы Mantine Т-Банка
    └── index.css         # Базовый CSS-reset
```
