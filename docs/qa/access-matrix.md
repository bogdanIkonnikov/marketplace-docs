# Матрица прав доступа и QA рисков

Матрица определяет доступ к операциям маркетплейса и связывает бизнес-риски с проверками. Её используем для согласования прав, проектирования API-тестов и выбора приоритетов автоматизации.

## Обозначения

Да — операция разрешена в пределах её бизнес-условий. Нет — запрещена по описанной модели ролей или бизнес-правилу. Свои — только объекты текущего пользователя или его магазина. Любые — объекты всех владельцев в пределах этой операции. ? — правило не определено или источники расходятся. — — отдельный сценарий для этой роли не описываем; это не утверждение об HTTP-ответе.

Обозначение со звёздочкой (*) означает покупательскую операцию только при наличии BuyerProfile. Продавец сохраняет покупательские возможности своего профиля. Администраторские права на товары и заказы не означают автоматически доступ к чужим корзинам и бонусному журналу.

Колонка «Покупатель» описывает аккаунт без прав продавца и админа. Колонка «Продавец» — работу с собственным SellerProfile и, при наличии, BuyerProfile. Совмещение ролей учитывается по конкретному действию.

## Переходы статусов

В таблице ниже продавец и админ действуют как операторы обработки заказов. Если тот же аккаунт отменяет собственную покупку, используется покупательское разрешение.

| Переход заказа | Покупатель | Продавец | Админ | Условие |
| --- | --- | --- | --- | --- |
| PAID → IN_PROGRESS | Нет | Свой магазин | Любой заказ | US-6.3 |
| IN_PROGRESS → COMPLETED | Нет | Свой магазин | Любой заказ | US-6.3 |
| PAID → CANCELLED | Свой заказ | ? | ? | US-6.2; возврат суммы этого заказа |
| IN_PROGRESS → CANCELLED | Свой заказ | ? | ? | US-6.2; окно отмены предложено пересмотреть в R-06 |
| PAID → COMPLETED либо IN_PROGRESS → PAID | Нет | Нет | Нет | Не предусмотрено графом; 409 |
| Из COMPLETED/CANCELLED в другой статус | Нет | Нет | Нет | Терминальные состояния; 409 |

Повтор отмены не должен приводить к новому возврату. Код ответа на повторный запрос и идемпотентный возврат исходного результата необходимо определить в API; запрет перехода из терминального статуса не отменяет необходимость безопасно обрабатывать повтор.

| Операция с товаром | Продавец | Админ | Условие |
| --- | --- | --- | --- |
| ACTIVE ↔ HIDDEN | Свой товар | Любой товар | US-3.4 |
| Физическое удаление | Свой товар | Любой товар | Только без ссылок из order_items |
| ARCHIVED → ACTIVE/HIDDEN | Нет | Нет | ARCHIVED — конечное состояние |

## 8 Как использовать матрицу в тестировании

Минимальные данные: покупатели A/B, продавцы A/B с покупательскими профилями, админ; товары обоих продавцов, изображения с разными правами, собственные/чужие корзины и заказы во всех статусах.

Для каждой операции со значением «Свои»:

- Выполнить разрешённое действие с собственным объектом и проверить результат.

- Повторить с чужим ID в пути, параметрах и теле запроса, если эти поля предусмотрены.

- Проверить списки, поиск, сортировку, страницы и метаданные на отсутствие чужих закрытых данных.

- Проверить запрос без токена, с недействительным и истёкшим JWT.

- При отказе убедиться, что закрытые данные не выданы и недопустимых изменений нет.

- Проверить разрешённые действия админа отдельно от запретов обычным пользователям.

Права проверяем через API. Скрытая кнопка не доказывает серверный запрет. Проверка статуса ответа дополняется проверкой состояния данных после завершения операции.

Уже заданные коды сохраняем: 403 для изменения чужого товара продавцом; 422 для самопокупки при добавлении и нехватки бонусов; 409 для недопустимых переходов статусов. Для остальных отказов точный код и формат ответа определяем в OpenAPI. Выбор 403/404 для сокрытия чужого объекта не распространяем автоматически на уже заданный 403 из US-3.3.

Связь с будущими тестами: идентификатор операции/риска → US → тест → результат прогона → дефект при наличии. Исполнителя и статус реализации двух QA назначаем в трекере; документ не сообщает, что проверки уже выполнены.
