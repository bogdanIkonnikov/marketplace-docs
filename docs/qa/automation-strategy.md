# Стратегия автоматизированного тестирования

## Источники и статус требований

User stories используются как рабочая основа для проектирования сценариев, без заявления, что команда уже утвердила каждый пункт. При конфликте источников QA фиксирует вопрос аналитику/команде и не выбирает правило молча.

## Область и очередность

В область автоматизации входят модульные, интеграционные и REST API-проверки всех 17 историй из US. Очерёдность берётся из story map:

- Сквозной поток: US-1.1 → US-1.3 → US-3.3 → US-2.1 → US-5.1 → US-4.1 → US-5.3 → US-6.3.

- Остальной MVP: US-1.2, US-1.4, US-2.2, US-3.1, US-3.2, US-3.4, US-5.2, US-6.1, US-6.2.

- Расширение отрицательных, конкурентных и отказных сценариев по рискам и изменениям приложения.

Обе первые группы относятся к MVP в предоставленной карте. «Остальной MVP» не переносится автоматическ и на четвёртый месяц. Не каждая проверка каждой истории обязана быть автоматизирована к первому показу: минимальный автоматизированный набор и оставшиеся ручные проверки согласуются явно. Ручные проверки интерфейса планируются отдельно.

## 5 Уровни и инструменты

| Уровень | Назначение и примеры | Предлагаемый инструмент |
| --- | --- | --- |
| Модульный | Расчёт суммы и количества, переходы статусов, валидация, проверка самопокупки как бизнес-правила. Без запуска Spring/БД | JUnit Jupiter; Mockito только для нужных зависимостей |
| Интеграционный внутри сервиса | Реальные миграции PostgreSQL, запросы владельца, уникальность email, транзакции и конкурентный доступ; загрузка/ссылки файлов с реальным MinIO | Spring Boot Test, Testcontainers, PostgreSQL/MinIO |
| API одного сервиса | HTTP-запросы, JWT и доступ, валидация и ответы по OpenAPI, результат операции | REST Assured и тестовый запуск сервиса |
| Межсервисный и сквозной через API | Совместная работа реальных сервисов, передача идентификаторов, таймауты и итоговые состояния покупки | REST Assured; способ развёртывания согласовать после определения сервисов |

| US-6.3 | Только свой магазин продавца/все заказы админа; PAID → IN_PROGRESS → COMPLETED; терминальные состояния; запрещённый переход 409 | Модульные + интеграционные + API |

Проверка хэширования пароля выполняется внутри изолированного теста хранения/проверки пароля; наличие нужных полей в API-ответе само по себе её не доказывает.

HTTP-коды, уже указанные в US, сохраняются в плане. Для остальных ошибок коды/структура уточняются в OpenAPI. Проверка схемы ответа дополняется проверкой бизнес-результата; соответствие JSON-схеме не доказывает правильность списания или разграничения прав.

## Риск ориентированный порядок автоматизации

P0 — первоочередные проверки целостности бонусов, заказов и доступа. P1 — остальные обязательные функции MVP.

| Риск из risks.md | Что проверяем / что требует решения | Приоритет |
| --- | --- | --- |
| R-01 | Потеря ответа после успешного checkout, повтор того же намерения покупки; поведение ключей после Q-05 | P0 |
| R-02 | Изменение цены между просмотром и оплатой; результат по утверждённому Q-06 | P0 |
| R-03 | Повторная проверка ACTIVE, владельца и самопокупки, состава и цены при checkout | P0 |
| R-04 | Товар физически удалён после добавления в корзину: нет битого состояния/частичного checkout; политика по Q-07 | P0 |
| R-05 | Повтор top-up не даёт непреднамеренное начисление после Q-05; лимит и самоначисление только после решения Q-09 | P0 |
| R-06 | Гонка отмены с завершением; одно допустимое итоговое состояние, возврат согласно выигравшему переходу; роли по Q-04 | P0 |
| R-07 | Нельзя случайно нарушить историю; результат DELETE/409 и необратимость ARCHIVED по Q-03 | P1 |
| R-08 | Пустая корзина/нулевая сумма: согласованный отказ без изменения состояния по Q-07 | P0 |
| R-09 | Не требовать складского лимита без включения остатков в scope; зафиксировать ограничение | Контроль scope |
| R-10 | Начальный статус товара; допустимость админского создания на seller_id; премодерация только после решения | P1 |
| R-11 | Комбинированные роли, старый JWT после изменения прав, самопокупка на checkout; политика актуальности по Q-09 | P0 для доступа |
| R-12 | BuyerProfile при обычной, продавцовской и служебной регистрации по Q-08 | P1 |
| R-13 | Формат ИНН по US; уникальность только после Q-09. Отсутствие доставки не считается дефектом MVP | P1 |
| R-14 | Согласованность баланса и журнала после top-up, оплаты, возврата и отказов; формулу принять отдельно | P0 |

Помимо этого реестра, из US обязательны проверки изоляции владельцев: два покупателя и два продавца, чужие ID в пути/параметрах/теле, списки и их метаданные, попытки менять роли и привязывать чужие изображения. Админские разрешения проверяем положительно, чтобы запрет всем не считался корректным разграничением.

При запрещённой операции проверяем ответ, отсутствие закрытых данных и отсутствие недопустимых изменений состояния. Публичность каталога не делает публичными корзины, заказы и бонусный журнал.

## Окружения и тестовые данные

- Модульные тесты запускаются локально и в CI без инфраструктуры.

- Сервисные интеграционные тесты используют изолированную PostgreSQL с настоящими миграциями. Для файловых сценариев поднимается MinIO.

- Межсервисный набор использует совместимые ревизии реальных сервисов в отдельном окружении.

- Общий тестовый стенд нужен для проверок развёрнутой сборки. Прогоны не чистят полностью общую БД.

Данные: покупатели A/B; продавцы A/B с покупательскими профилями; доверенно созданный админ; товары обоих продавцов в ACTIVE/HIDDEN/ARCHIVED; корзины с одним/двумя продавцами; заказы во всех четырёх статусах; общие/отдельные картинки; балансы меньше, равные и больше суммы.

Каждый тест сам создаёт необходимые объекты с уникальными идентификаторами и не зависит от порядка запуска. Подготовка через репозиторий/фикстуру допустима в изолированных тестах; сквозной поток использует реальные API, кроме явно отмеченных начальных фикстур. Проверяемая операция не подменяется прямой записью в БД.

Для транзакций проверяется состояние после фактического завершения запроса. Откат транзакции самого теста не должен скрывать ошибки сохранения. На общем стенде очистка затрагивает только данные своего прогона.

Конкурентные запросы стартуют управляемо, затем проверяются все ответы и итоговые данные. Отдельно воспроизводятся сбой между шагами, таймаут зависимости и потеря ответа после сохранения. Механизм внесения сбоев определяется вместе с backend и работает только в изолированном окружении.

## План по этапам

| Этап | Результат |
| --- | --- |
| Подготовка до первых функций | Распределение QA, перечень сервисов, контракт первой функции, шаблон тестов и первый CI-прогон |
| По мере готовности сквозного потока | Модульные проверки бизнес-правил, API каталога/доступа, затем top-up → корзина → checkout → статус; ошибки оплаты проверяются вместе с оплатой |
| До показа MVP через 2 месяца | Основной сквозной API-прогон, P0 для реализованных оплаты/возврата/прав, проверка всех принятых MVP-историй автоматизированно или с явно указанным ручным покрытием; известные ограничения и открытые вопросы отражены в отчёте |
| Между MVP и финалом через 4 месяца | Закрытие согласованных пробелов автоматизации, расширение отказных/конкурентных сценариев, межсервисной совместимости и стабильности CI; поддержка новых изменений |
| Перед финальным показом | Полный актуальный регресс, повторная проверка критичных рисков, отчёт о результатах и оставшихся ограничениях |

Точное число автотестов и сроки отдельных наборов определяются после первого рабочего примера и оценки скорости обоих QA. Месяц 3–4 не считается резервом для обязательных функций MVP без пересогласования scope.

## 11 Запуски отчёты и сопровождение

Предлагаемая площадка — GitHub Actions из исходной концепции; её доступность и права команды нужно подтвердить.

| Событие | Проверки |
| --- | --- |
| Pull request сервиса | Модульные, затронутые интеграционные и доступные критичные API-проверки в изолированном окружении |
| Изменение OpenAPI | Проверка соответствия схем/кодов и затронутых потребителей; при ломающем изменении — межсервисный прогон |
| Развёртывание совместимой сборки | Короткая проверка работоспособности API и критичный сквозной поток |
| Перед демонстрацией/после значительных изменений | Полный актуальный набор, отказные/конкурентные сценарии, ручные проверки областей без автоматизации |

Первый этап — измерить время и стабильность. Затем команда назначает обязательные проверки перед слиянием. Полный межсервисный набор не запускается на каждом изменении автоматически, пока неизвестна стоимость такого прогона.

Отчёт содержит: ревизии всех сервисов, окружение, время прогона, passed/failed/skipped, привязку тестов к US/рискам, причину пропуска, обезличенные запрос/ответ и диагностические данные, ссылки на дефекты. Ошибка среды отделяется от дефекта приложения, но тоже требует разбора.

Неустойчивые тесты получают задачу, владельца и срок исправления. Повтор прогона не скрывает первое падение. Критичный пропущенный/отключённый тест не считается пройденным.

По результатам фиксируем:

- Какие принятые критерии и P0-сценарии реально покрыты и прошли, какие ещё проверяются вручную.

- Какие проверки отсутствуют/заблокированы и почему.

- Продолжительность и стабильность наборов.

- Открытые дефекты и остаточные риски.

Процент покрытия кода можно использовать для поиска пробелов; требование 100% или другой произвольный порог пока не устанавливается.
