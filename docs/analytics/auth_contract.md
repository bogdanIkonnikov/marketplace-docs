# Контракт Auth Service

[Скачать спецификацию OpenAPI 3.1 (YAML)](/openapi/auth.yaml)

Спецификация описывает целевой HTTP API для [разделов 2.1 и 2.2 REST-спецификации](./api_specification.md#2-auth-service). В текущем бэкенде HTTP-слой Auth ещё предстоит реализовать.

## Согласовано для MVP

- Аккаунт имеет одну роль и уникальный email. Публичные маршруты создают аккаунты BUYER и SELLER. После регистрации продавец сразу получает доступ к своей роли. ADMIN назначается вне публичного API.
- Пароль при регистрации содержит не менее 8 символов. При входе проверяются наличие пароля и учётные данные. ИНН передаётся строкой из 10 или 12 цифр и задаётся при регистрации.
- Access JWT передаётся в JSON и используется в заголовке `Authorization: Bearer …`. Refresh JWT хранится в cookie `refreshToken` с атрибутами `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. Записи refresh-сессий в БД отсутствуют.
- Refresh выпускает новую пару токенов и обновляет cookie. Logout проверяет access JWT и сбрасывает cookie. Ранее выпущенный refresh JWT остаётся действительным до истечения своего срока, если его подпись и аккаунт по-прежнему действительны.
- Некорректный JSON даёт `400`, занятый email — `409`, ошибки полей — `422`. Ошибки передаются как `application/problem+json`. В `422` поле `details` содержит одно сообщение на поле в формате `Record<string, string>`.

## Как контракт соотносится с кодом

| Источник | Состояние |
|---|---|
| Backend `main` (`722a87e`) | Корневой Spring Boot запускается, `auth` подключён как подпроект Gradle с каркасом каталогов. В приложении нет контроллеров Auth, HTTP DTO, JWT-фильтра и подключения домена к PostgreSQL. |
| Backend `feat/auth-folder-structure` (`8b255dc`) | Реализованы доменные сценарии регистрации, входа, refresh, logout и профиля с одной ролью, а также выпуск access JWT на 15 минут и refresh JWT на 30 дней. `PasswordPolicy` пока проверяет только непустое значение. Комментарии к доменным исключениям предлагают `400` для части ошибок полей, HTTP-маппинг предстоит привести к `422`. |
| Backend `feat/auth-db` (`be40d1c`) | Есть миграция Flyway, JPA-сущность и репозиторий для `auth.users`. Миграция задаёт `UNIQUE` для email и ИНН. Эта ветка пока отдельно от доменных сценариев и запускаемого приложения. |
| Frontend `main` (`cce6c04`) и `develop` (`9c7b9d0`) | Axios отправляет credentials и Bearer JWT, хранит access-токен в памяти и восстанавливает сессию через refresh. После refresh клиент запрашивает `/api/v1/user/profile`. Вход при ошибке API возвращает данные заглушки. |
| Frontend `feat/auth-forms` (`2e80f9e`) | Добавлены форма и запрос регистрации покупателя. Клиент требует ФИО и 6 символов пароля, читает access-токен из `localStorage` и также запрашивает `/api/v1/user/profile`. Вход и регистрация при ошибке API возвращают данные заглушки. Сквозная обработка `409` и `422` с `details` пока отсутствует. |

Для OpenAPI использован маршрут `/api/v1/users/me` из REST-спецификации. Вход и обе регистрации возвращают `{ accessToken, user }` по формату ответа, который использует фронтенд. Refresh возвращает `{ accessToken }`. Поля объекта `user` и ответа `/users/me` взяты из доменной модели `UserProfile`. В неё входят скалярный `role`, `fullName` и реквизиты соответствующей роли. Клиентский тип `User` сейчас ожидает `roles[]`, `name`, `buyerId` и `bonusBalance`. При интеграции понадобится обновить маршрут и тип клиента либо согласовать преобразование DTO. Порт контейнера `8081` можно передать в Vite через `VITE_BACKEND_URL=http://localhost:8081`.

[ER-модель](./database_er_diagrams.md) и бэкенд-ветки поддерживают модель одной роли. [User Stories](./user_stories.md) и [матрица доступа](../qa/access-matrix.md#аккаунты-и-профили) описывают совмещение ролей. [Фронтенд-контракт](../frontend/api_contracts.md) включает организации и членство в них. [Черновик бизнес-правил](./business_rules_questions.md) предлагает подтверждение продавцов администратором. Эти различия важны при обновлении критериев приёмки и тестов Auth.

## Открытые вопросы

- **Хранение access-токена на клиенте.** Ветка форм использует `localStorage`, основные ветки — память. HTTP-контракт поддерживает оба варианта через Bearer JWT.
- **Уникальность ИНН.** Миграция ветки БД содержит `UNIQUE`. Для MVP правило и HTTP-ответ при повторном ИНН остаются открытыми. `409` в текущем OpenAPI относится к занятому email.

## Проверка

Выполните из корня репозитория документации.

~~~powershell
python -m pip install openapi-spec-validator==0.9.0
python -m openapi_spec_validator static/openapi/auth.yaml
npm ci
npm run build
~~~

YAML можно открыть в Swagger Editor как отдельный файл. Проверка синтаксиса OpenAPI и сборка сайта не требуют запущенного API.
