# Спецификация REST API микросервисов — Мобильный маркетплейс

**Проект:** Мобильный маркетплейс (Т-Образование, JDEPH-93)  
**Архитектура:** 4 микросервиса (`Auth & Profile`, `Media`, `Catalog & Search`, `Commerce`) + PostgreSQL (Database-per-Service через логические схемы/базы) + MinIO (S3)  
**Формат обмена:** Только REST API (JSON). Взаимодействие через gRPC и GraphQL исключено требованиями ТЗ.

---

## 1. Общие стандарты и конвенции API

### 1.1. Аутентификация и авторизация (JWT + HttpOnly Cookie)
В соответствии с лучшими практиками безопасности (OWASP) и требованиями ИБ:
- **`accessToken`** (короткоживущий, ~15 минут):
  - Возвращается в JSON-теле ответа (`{ "accessToken": "..." }`).
  - Хранится на фронтенде исключительно в памяти приложения (React state / closure).
  - Передаётся в заголовке запросов: `Authorization: Bearer <access_token>`.
- **`refreshToken`** (долгоживущий, ~7-30 дней):
  - Передаётся бэкендом через заголовок **`Set-Cookie`** с атрибутами:  
    `Set-Cookie: refreshToken=<token>; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age=2592000`
  - Недоступен для чтения из JavaScript (`document.cookie`), что исключает кражу сессии через XSS-атаки.
  - Автоматически отправляется браузером только на эндпоинты `/api/v1/auth/refresh` и `/api/v1/auth/logout`.
- **Payload токена Access JWT:**
  ```json
  {
    "sub": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "roles": ["ROLE_BUYER", "ROLE_SELLER"],
    "buyer_id": "8a0e1c2b-3c4d-5e6f-7a8b-9c0d1e2f3a4b",
    "seller_id": "5b1f2c3d-4e5f-6a7b-8c9d-0e1f2a3b4c5d",
    "admin_id": null,
    "exp": 1730000000
  }
  ```

### 1.2. Идемпотентность (Idempotency-Key)
- Заголовок `Idempotency-Key: <UUID>` **строго обязателен** для мутирующих финансовых операций:
  - `POST /api/v1/orders/checkout` (R-01)
  - `POST /api/v1/admin/wallets/{buyerId}/top-up` (R-05)
- Повторный запрос с тем же ключом и тем же пользователем возвращает сохранённый ответ без повторного списания или начисления средств.

### 1.3. Фильтрация, сортировка и пагинация списков
В соответствии с требованиями ТЗ:
- **Фильтрация:** `f[<поле>]=<значение>` (диапазон через запятую: `f[price]=100,500`; отрицание: `f[sellerId]!=...`).
- **Сортировка:** `sort=<поле>,<asc|desc>` (например, `sort=price,asc` или `sort=createdAt,desc`).
- **Пагинация:** `page=0&size=20` (нумерация с 0).
- **Ошибки параметров:** При невалидном диапазоне (`min > max`), неизвестном поле или отрицательном `page` возвращается `400 Bad Request` (US-2.2 AC 4).

### 1.4. Формат ошибок (RFC 7807 Problem Details)
Все ошибки возвращаются в едином формате:
```json
{
  "type": "about:blank",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "Нельзя добавить в корзину товар собственного магазина",
  "instance": "/api/v1/cart/items",
  "timestamp": "2026-10-30T18:30:00Z"
}
```

## 3. Media Service
**Порт по умолчанию:** `8082`  
**Префикс пути:** `/api/v1/media`  
**Схема БД:** `media`  
**Хранилище:** MinIO (S3 bucket: `marketplace-media`)  
**Архитектура загрузки:** Прямая загрузка в S3 через Presigned URLs (снижает нагрузку на сеть и память бэкенда).

| Метод | Путь | Доступ | Описание | US / Риск | Коды ответов |
|---|---|---|---|---|---|
| `POST` | `/upload` | Продавец, Админ | **Инициализация загрузки:** клиент передаёт `{ fileName, contentType, sizeBytes }`. Валидация формата (JPEG/PNG/WEBP, до 10MB). Создаётся запись со статусом `PENDING`, генерируется временный S3 Presigned PUT URL. Возвращает `{ mediaId, uploadUrl, expiresAt }`. | US-3.1, CT-04 | `200 OK`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `413 Payload Too Large`, `415 Unsupported Media Type` |
| `POST` | `/{mediaId}/confirm` | Автор файла, Админ | **Подтверждение загрузки:** вызывается после прямого `PUT` файла фронтендом в MinIO. Сервис проверяет наличие файла в S3 через `HeadObject`, переводит статус в `CONFIRMED` и возвращает `{ id, publicUrl, status }`. | US-3.1 | `200 OK`, `400 Bad Request`, `404 Not Found` (файл не найден в MinIO) |
| `GET` | `/{mediaId}` | Любой | Получение метаданных изображения (URL, размер, content-type, статус). | US-3.1 | `200 OK`, `404 Not Found` |
| `DELETE` | `/{mediaId}` | Автор файла, Админ | Удаление изображения из MinIO и метаданных (если не привязано к товарам). | US-3.1 AC 4 | `204 No Content`, `403 Forbidden`, `404 Not Found`, `409 Conflict` |

## 6. Матрица статус-кодов для типичных сценариев
- `200 OK` — Успешное чтение или обновление ресурса.
- `201 Created` — Успешное создание ресурса (содержит заголовок `Location` или созданную сущность в теле).
- `204 No Content` — Успешное удаление без тела ответа.
- `400 Bad Request` — Синтаксическая ошибка входных параметров (неверный формат фильтра, min > max).
- `401 Unauthorized` — Отсутствует или просрочен JWT токен.
- `403 Forbidden` — Токен валиден, но прав роли недостаточно (например, продавец редактирует чужой товар/заказ).
- `404 Not Found` — Запрашиваемый ресурс не найден.
- `409 Conflict` — Конфликт бизнес-состояния (повторная регистрация занятого email; недопустимый переход статуса заказа; удаление товара с заказами; попытка изменить цену на лету).
- `422 Unprocessable Entity` — Семантическая ошибка валидации (самопокупка в корзине; нехватка бонусов на чекауте; неверный формат ИНН; сумма начисления &le; 0).
